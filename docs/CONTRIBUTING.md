# Contributing to the CAIBI public catalogue

CAIBI welcomes corrections, better sources and firsthand build evidence. The most useful contribution starts by identifying which evidence voice it belongs to.

## SOURCE correction

Use this when the original project or manufacturer information is wrong, stale or has moved.

Please include:

- the affected project slug or record;
- the field or statement that needs correction;
- the current public source URL;
- a short explanation of what changed.

Examples include a repository moving, a manufacturer replacing a product page, a BOM changing or a published specification being updated.

## CAIBI assessment challenge

Use this when you think CAIBI's synthesis, verdict or factual assessment needs reconsideration.

Please include:

- the affected project slug;
- the assessment field or verdict you are challenging;
- the evidence that supports the challenge;
- whether the evidence is a primary source, independent review or firsthand build experience.

A contribution can trigger editorial review but does not automatically change a verdict.

## BUILDERS evidence

Firsthand reports are especially useful when you actually attempted or completed a build.

Useful details include:

- whether it worked first time, worked after changes, was abandoned or led you to buy something instead;
- what you changed from the published source;
- approximate cost and time where you are comfortable sharing them;
- links to a public write-up, repository, MakerWorld, Printables, video or site;
- practical problems that the original source did not make obvious.

Do not add private contact information to a public issue or pull request.

Uploaded build photos are not accepted directly into the public dataset through GitHub at this stage. CAIBI only publishes submitted media after rights and safety checks, so use the website's builder-report route for photo evidence.

## Keep the evidence voices separate

Do not rewrite a SOURCE claim as if it were a CAIBI conclusion, or an individual builder report as if it represented every build.

Where evidence conflicts, preserve the disagreement. That is useful information.

## Data changes

Public data must conform to the schemas in `schema/` and the rules in `docs/DATA-CONTRACT.md`.

Unknown values should remain unknown. Do not estimate cost, time or specifications simply to fill a field.

For assessed projects, SOURCE, CAIBI and BUILDERS evidence remain distinct. Material contradictions should be surfaced for review rather than silently resolving themselves through an automated edit.

## Scope

This repository is for public catalogue, evidence, schema and community material. Please do not submit application code, deployment configuration, infrastructure details, credentials, private moderation material or personal data here.
